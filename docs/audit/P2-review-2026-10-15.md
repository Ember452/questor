## 1. 一句话结论

**NO-GO（有条件）** —— P2 的三条 ROADMAP 安全 DoD（危险操作触发 `ask`、`deny`/敏感路径不可越、非法参数被拒）**已由真实工具 + 真实审批闭环端到端跑通并证明**，且 P0/P1 审计的全部 Blocker（C2 假不可变、Cancel seq 碰撞、checkpoint/resume、护栏梯度、沙箱 fail-closed、策略异常兜底）**均已闭环**；但对抗必查清单暴露 **3 个当场复现的不变式/安全判定违规**——(a) 工具 panic 未被 Harness 兜底转 error（design/03 §8 line121 明确要求、必查#7、未实现且无测试）；(b) `FinalizeRun(failed)` 不回填未闭合 `tool_use`，留下无 `tool_result` 的悬挂调用（复现：`open call still PENDING=True, tool_result present=False`，违 C7/I1）；(c) shell parser **不做 flag 簇展开**，`sed -ni` 被误判为只读（复现：`sed -ni all_read_only=True`），在 job/partial + full_auto 下可跳过审批——外加一批**无消费者的安全/扩展死字段**与 **`wrap_shell` 缺失**。**须关闭 §6 必须修（#1–#4 阻断级）后方可复评进 P3。** 判定宁严不宽。

## 5. 扩展有害项（前瞻反噬 · 具体到 Phase）

1. **`FinalizeRun` 不回填 open 调用 → 反噬 P3（durable resume/回放）**：已复现 failed 留 `tool_use` 无 `tool_result`（§8-F）。P3 做 `after_seq` 续传与从快照+事件尾部重建 `Domain_State` 时，会把这条**未配对 conversation 直接喂回 provider**（Anthropic/OpenAI 强制 tool_use↔tool_result 成对，否则 4xx），且 resume 会把它当作"可继续的在途工具"复活 → 与 ADR-0016 生命周期铁律冲突。越晚修，越要在 reduce 终态处统一补 `_backfill_open_calls` 并重放历史验证。
2. **`sed -ni` 等 flag 簇误判只读 → 反噬 P2 自身安全承诺 + P5/P9**：parser 不展开短 flag 簇（复现 `sed -ni all_read_only=True`，§8-C）。在 **job/partial + full_auto** 下，`bash -lc "sed -ni ..."` 这类原地改写会被判 "proven read-only" → 跳过 exec ASK floor → **自动放行有写副作用的命令**。这是对 "无写围栏→ask/deny"（ADR-0015）的实质破口，也是未来接真沙箱后仍潜伏的解析层缺陷。
3. **`orchestrator/barrier/parallel_safe` 假扩展位 → 反噬 P5（并行）/P6·P8（子 agent）**：三者零消费者（§4-A）。P5 作者若以为 "设了 `barrier` 就同批独占、`parallel_safe` 就能并发"，会**在并不存在的 gate 上叠逻辑**；真接线时又要返工内核。至少要显式 `# NOT enforced until P#` 标注并从 provider 可见面剥离。
4. **`PermissionCtx.denylist` 假控制面 → 反噬 P4（记忆/策略可插拔）**：ADR-0014 把 denylist 列为权威真源，用户/上层若通过 `SetPermission*` 或配置追加自定义敏感路径，**求值根本不看它**（§8 grep）。P4 引入可配置策略时会误信这条接缝已通，实际加的路径不设防。
5. **`wrap_shell` 缺失 → 反噬后续平台沙箱（seatbelt/bwrap 实机）**：design/03 §4 line76-78 要求 `wrap_shell`/`wrap_argv` 分离；当前只 `wrap_argv`（§8 grep）。真正接 seatbelt/bwrap 的 shell 级 profile 包装时缺该接缝，只能把命令塞回 argv 或临时补 API，破坏 ADR-0017 "argv 不拼回 shell string" 的可验证边界。
6. **文件工具无 deadline → 反噬 P2/P3 可靠性**：`spec.timeout_s` 仅记录不入执行链（§3-C8）。挂死的 `read`（网络盘/巨文件）不受 Harness 超时约束，长跑会把单写者循环整段卡住；与 03 §8 line118 "每个工具由 ProcessRunner 武装 deadline" 的承诺不符（实际只 exec 工具经过 ProcessRunner）。
